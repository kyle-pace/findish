## Development principles

These apply to every project Kyle builds, on any platform, with any agent. The project's own section of this file adds specifics and can override a default for that project. Kyle's direct instructions in a session override both.

### Priority order

When two goals conflict, the higher one wins:

1. Accessibility
2. Privacy
3. Correctness and reliability
4. Performance
5. Polish

### Accessibility comes first

Accessibility is designed in from the first commit, not audited in at the end.

- Meet WCAG 2.2 AA at minimum. Text contrast is at least 4.5:1 (3:1 for large text and for UI parts like borders and icons), in both light and dark mode.
- Use semantic, native elements first (`button`, `a`, `label`, headings in order, landmarks). Add ARIA only when no native element does the job.
- Everything interactive works with a keyboard, has a visible focus style and has an accessible name. Touch targets are at least 24×24 px; aim for 44×44.
- Never carry meaning with color alone. Meaningful images get alt text; decorative ones get empty alt.
- Respect user settings: reduced motion, light/dark preference, text zoom to 200% without breaking layout.
- Motion is short (under 300 ms for interface animation) and never `ease-in`.
- On the web, motion only runs inside `@media (prefers-reduced-motion: no-preference)`.

### Every screen size from day one

Layouts are designed for phones, tablets and big screens from the first commit, not stretched or squeezed in later.

- **Web projects** are fully responsive: mobile first, fluid from 320 px wide up to large desktop monitors. No sideways scrolling at 320 px. Cap line length for reading (about 70 characters), and let wider screens add columns instead of stretching text.
- Prefer fluid layouts (flexbox, grid, `clamp()`, container queries) over many fixed breakpoints.
- Handle touch, mouse and keyboard on every size, and respect safe areas and notches.

### Type

- Atkinson Hyperlegible Next for all text and Atkinson Hyperlegible Mono for code, in every product.
- Self-host the fonts. Never load them from Google Fonts or any other font CDN.
- On the web, use the `@fontsource/atkinson-hyperlegible-next` and `@fontsource/atkinson-hyperlegible-mono` packages.
- Offering a setting to switch to the device's own font is fine.

### Privacy comes second, and right behind

- Collect the least data that answers a real product question. No ad or marketing pixels, no fingerprinting, no selling or sharing data.
- Never put personal information in analytics: no names, emails, free-text input or precise location.
- Respect Global Privacy Control and Do Not Track by sending no analytics at all, and give people an opt-out.
- No cookies for analytics (keep the ID in `localStorage`), so no cookie banner is needed.
- Analytics only runs on the live production domain, never on localhost or preview builds.
- Any project that collects data has a short, plain-language privacy page.
- Secrets never go in Git. (Browser API keys that are public by design, like Amplitude's, are fine in code.)
- Every key comes from Kyle's one key store through `.agents/keys.json` and `~/Developer/ops/scripts/sync-keys.mjs`; never type a key into a project or ask for one in chat. Follow the `project-keys` skill when a project needs a key.

### Default stack

Use these unless the project's section says otherwise. **Do not add any other third-party service, SDK, script, font or paid tool without asking Kyle first.**

- **Product analytics: Amplitude**, set up the private way:
  - on the web, use `startAnalytics` from kp-design's `kp-design/analytics`, which does all of this
  - autocapture on, IP address tracking off, identity in `localStorage`
  - off under GPC, Do Not Track or the opt-out; only on the live domain
  - Session Replay only if the project wants it: a small sample (about 5%), conservative masking, and its code only loaded for sampled sessions
  - custom events follow the naming rules under "Analytics events" below
- **Backend: Firebase** (Auth, Firestore, Functions, Storage) when a project needs accounts or shared data.
  - Security rules deny by default and are locked down before anything ships.
  - Firebase Analytics stays off; Amplitude covers analytics.
- **Web hosting: Cloudflare** (Workers with static assets). GitHub Pages is fine for a simple static site.
- **Design system for Kyle's websites: [kp-design](https://github.com/kyle-pace/kp-design)**, installed from GitHub and pinned to a commit. It holds the tokens, self-hosted Atkinson, header, footer, display settings and analytics; projects on kylepace.dev use its `DevLayout`. Don't copy these into a project; change them in kp-design. (Apple apps don't use it.)
- Put each outside service behind its own module (one file talks to Amplitude, one to Firebase), so switching tools means changing one file.
- CI checks the stack on every push: Amplitude is in every site and app, Firebase Analytics isn't, each Firebase config file is for a bundle ID the app really has, and Firestore rules aren't open. It can't see inside the Amplitude or Firebase consoles, so settings there (APNs keys, API key restrictions, a separate production project) still need a person.
- Keep running costs near zero: prefer static pages, free tiers and on-device work, and ask before adding anything that bills.

### Analytics events

Every project uses the same rules, so charts read the same way everywhere.

- **Event names:** Title Case, past-tense verb first, then the object: "Saved Recipe", "Viewed Deal", "Completed Onboarding". Not "Recipe Saved" and not `save_recipe`. Use the same verb for the same action across projects (Viewed, Opened, Tapped, Added, Removed, Changed, Saved, Completed).
- **Property names:** lowercase `snake_case` (`deal_id`, `stores_picked`). Keep names and values the same across events and projects when they mean the same thing.
- Leave Amplitude's own `[Amplitude] …` events alone. Add custom events only for actions that answer a real product question; autocapture covers page views and clicks.
- **One Amplitude project per product.**
- kylepace.dev and every experiment on it share the kylepace.dev project, so each experiment's custom events also send `experiment` with the project's slug (`experiment: "skill-tree"`).
- **Every new feature ships with its events.** Building a feature includes its analytics: the events that say whether people find it and use it, written in the same change as the feature, not left as a follow-up. Say in your report which events you added, or why the feature needs none.
- **Tracking plan first:** add each new event and its properties to the project's tracking plan in Amplitude, with a description and category, as part of the same piece of work. Do it yourself when you can reach Amplitude; if you can't, say so and list exactly what needs adding. Nothing should arrive as "unexpected".
- **Renaming an event:** rename it in code, then merge the old name into the new one in Amplitude so history stays connected. Don't rename in Amplitude alone.
- **New product:** create its Amplitude project and add a row for it to the "All projects overview" dashboard. A new experiment on kylepace.dev needs neither: it appears there by page path.

### Self-host everything; approve outside hosts one at a time

- Serve libraries, fonts and assets from the project itself. Install them from npm and bundle them, or keep a pinned copy in the repo (for example in `vendor/`) with a script that refreshes it.
- Never load them from a CDN like jsDelivr, unpkg or cdnjs.
- **Scripts, styles, fonts and APIs** from an outside host need Kyle's OK every time. Approvals are per project and per host. Once he approves, add the host to that project's `.agents/allowed-hosts.txt` with a comment saying what it's for and the date he approved it.
- **Images** are lighter, because an outside image can only learn that someone visited, not run code. An image host can be added without asking when the image belongs to the content being shown (a recipe site's own photo on a result for its recipe, a book's cover from the library that lists it). Load those images with `referrerpolicy="no-referrer"` and `loading="lazy"`, add the host to `.agents/allowed-hosts.txt` with a comment saying what it's for, and mention the new host to Kyle when you report back. Decorative images, stock photos and anything that looks like tracking still need his OK.
- All of this applies to hosts that JavaScript calls at runtime too, even though the CI check only sees HTML and CSS. List those in the same file.

### Look and feel: no generated defaults

- Before building a page or app's look, write a short plan in `design/PLAN.md`: the subject and who it's for, the one bold element, 4 to 6 named colors (light and dark), and the layout as a sketch. Take the ideas from the subject's own world, not from other websites. If a frontend-design skill is available, load it.
- Check the plan against the generated defaults and change anything that matches: a big headline over a muted sentence and a pill button; pills or one corner radius on everything; grids of identical cards; small labels above headings; colored dots or squares as decoration; details joined with middle dots; monospace for small labels; copy that explains the interface instead of using it.
- Spend boldness in one place and keep the rest quiet. Look at screenshots (phone and desktop, light and dark) before calling it done.
- Experiments on kylepace.dev are their own pages (kp-design's `LabLayout`) with their own look. The app comes first; the explanation goes on its About page, linked from the top bar.
- About pages use the same title, headings and step format everywhere (the `about-page` skill). The look can follow the project's theme; the words never do.

### How things get built

- Static and simple by default. Add JavaScript, servers or dependencies only where they earn it.
- Colors, type and spacing live in one tokens file. Light and dark mode exist from the start.
- Copy is plain language, written for the person using it.
- Don't add "Built with AI" lines or other AI credits to sites or apps unless Kyle asks.

### Docs stay current

Docs are part of the change, like its analytics events: the same piece of work updates every doc that describes what changed, in every project it touches. Not a follow-up, and not only when a session ends.

- **In the repo:** the README (what it is, how to build and run it), the project's section of this file, and any handoff or status file the project keeps (where things stand, decisions, what's left).
- **In Confluence:** the project's pages in the App Projects space (https://kylepace.atlassian.net/wiki/spaces/APPS). Update the status line and date on the project's overview page and the pages about what changed (architecture, analytics, notifications, roadmap and so on). A new feature that needs more than a few lines gets its own page under the project's. Do it yourself when you can reach Confluence; if you can't, say so and list what needs changing.
- The project's section names its Confluence overview page. A project with none yet gets one with its first real feature.
- Write for someone picking it up cold: what it does, how it works, where it stands, and the date. When something stops being true, change or remove it; don't add the new fact beside the old one.
- Say in your report which docs you updated, or why the change needed none.

### Correctness

- Anything that reads data from outside the project (a feed, a flyer, an API response, a file someone picks) gets a test that runs it against a saved real sample, plus one broken sample.
- One bad record never takes down the rest: skip it, log it, and keep going.
- A scheduled job that fails must fail out loud (a red run), and must never replace good published data with empty or partial data.
- A bug fix comes with a test that fails without the fix, when the project has tests.

### Performance

Budgets, not goals. If a project needs to go over (a map, a globe, a video player), its section says so and by how much.

- Content pages ship no more than 50 KB of JavaScript (compressed), and read fine without it.
- No single image over 200 KB. Images are sized to how they're shown, served as AVIF or WebP, given `width` and `height`, and lazy-loaded below the first screen.
- On a mid-range phone: the main content shows within 2.5 seconds (Largest Contentful Paint) and the layout shifts less than 0.1 (Cumulative Layout Shift). Lighthouse performance is 90 or higher on mobile.

### Shipping

- Small commits, each with a plain sentence saying what changed for the person using it.
- Websites deploy from `main`. Once the checks for the change's tier pass (see "Before you call it done"), push to `main`; no need to wait for Kyle. Use a branch and pull request when he asks for one, or when you want him to look before it goes live.
- Never force-push `main`, skip a failing check to get something out, or commit a secret.
- Changing the principles or kp-design changes every project. Test the change against one real project first, then roll it out.
- **Ask Kyle first, every time:** anything that costs money; a new outside service, SDK or host (see above); DNS, domain or email changes; deleting data, a repo or a deployed project; making a private repo public or a public one private; publishing something he hasn't linked publicly yet (a draft, a case study, an unannounced app); anything that speaks for him (his résumé, LinkedIn, a post or message in his name).
- When Kyle has to do a step himself (approve a setting, create a repo, sign in), give him the direct link to the exact page.
- If you couldn't finish or couldn't check something, say so plainly in your report. Don't describe work as done when a step was skipped.

### Teach Kyle as you go

Kyle is a product leader building his development skills through this work. Treat each session as a chance to teach, briefly.

- When a change involves a real decision (data structure, architecture, a library, security, performance, a tradeoff), explain it in plain language: what you chose, the main alternative, and why. A short paragraph, not a lecture.
- After making changes, show the most important part of the diff and walk through what it does in plain terms. Point out one thing worth learning from it.
- Define jargon the first time it comes up in a session.
- When a change is small and safe (a color, copy, a value, spacing), offer to let Kyle make it by hand, and tell him which file and line to change.
- Skip all of this for trivial changes like typos and formatting.

### Every new page or project ships with

- A share card (Open Graph image, 1200×630) in dark mode, using Atkinson. Follow `.agents/skills/share-card/SKILL.md`.
- A real title, description and favicon.
- A privacy note if it collects anything.

A new website on its own domain also gets set up so search engines can find it, as part of launch, not later:

- A home page title that says what the site is and who it's for ("Henwood: pantry and recipes app for iPhone, iPad and Mac"), not just the name.
- `robots.txt` that points to a sitemap, and a sitemap that lists every page meant to be found. Astro sites use `@astrojs/sitemap`; a hand-written site keeps `sitemap.xml` by hand and adds each new page to it.
- Structured data (JSON-LD) on the home page: `WebSite` for every site, `MobileApplication` with the store or TestFlight link for an app's site, and Kyle's `Person` (`@id` `https://kylepace.net/#kyle`) on his personal sites.
- A Google Search Console domain property with the sitemap submitted, the site imported into Bing Webmaster Tools, and IndexNow pinging Bing after every deploy. Follow `.agents/skills/search-setup/SKILL.md`. Verifying the domain adds a DNS record, so ask Kyle first (see "Shipping").
- A few days after launch, check Search Console's Pages report and fix anything it says it couldn't crawl.
- Changing a favicon later? Give the new file a new name (`favicon-v2.png`), because Google keeps showing the old one for weeks otherwise.

### Before you call it done

Match the checking to the change. If you're unsure which tier a change is, use the higher one. In your report, say which tier you used and what you ran.

**Tier 1: words and data.** Copy, a link, a value in a data file, a dependency pin, docs.

- The build passes, and so do any tests and linters.
- Read the changed text where it shows up in the built output.
- The docs that describe what changed are updated, in the repo and in Confluence (see "Docs stay current").

**Tier 2: something people see or use changed.** Layout, styles, a component, a new control, new behavior.

- Everything in tier 1.
- A new feature has its events in code and in the Amplitude tracking plan (see "Analytics events").
- Run the project's check command (`npm run check` where a project has one). It runs axe on every page in light and dark, fails on sideways scrolling, and saves screenshots at 320, 768, 1280 and 1920 px. Fix what it finds.
- Look at the changed screen in light and dark, at the smallest size and a large one.
- Use new controls with the keyboard (and VoiceOver in apps): reachable, visible focus, a name that makes sense.

**Tier 3: a new page, screen or project, or a redesign.**

- Everything in tier 2.
- Look at every size in light and dark: 320, 768, 1280 and 1920 px wide.
- Check it at 200% text zoom (the largest Dynamic Type size in apps) and with reduced motion on.
- Everything under "Every new page or project ships with".
- Check it against the performance budgets.

CI runs the check command where a project has one, the stack check (see "Default stack"), and a third-party check that fails if a page loads scripts, styles, fonts or images from a host that isn't allowed. Don't add a host just to get past it: ask Kyle, or for a content image follow the image rule above.

## This project: Findish

Findish (findish.now; called Recipe search until 2026-11-16, when it moved off kylepace.dev/recipe-search/ to its own domain). One search box across the recipe sites Kyle trusts, from our own small index instead of Google. Part of the App Projects family with Seattle Grocery Deals and Henwood. The repo was called recipe-search until 2026-11-22.

- **Plan and decisions** live in Confluence: App Projects space (APPS), page "Findish" (6848557) and its child pages. Keep it current when anything here changes.
- **Docs mirror** in the claude.ai App Development project: `recipe-search/overview.md`.

### Rules for collecting data

- Respect every site's robots.txt and terms. Check robots.txt on every run, and skip a site that starts blocking us.
- Keep only what's needed to find a recipe: title, link, photo link, ingredient names, total time, cuisine, course, yield. Never the method, headnotes, comments or ratings text. Every result links to the original.
- Crawl slowly: one request at a time per site, a few seconds apart. Identify the crawler by name (FindishBot) with a contact page.
- Read sitemaps and fetch only pages that are new or changed.
- Newsletters (Substack and other sites with an RSS feed but no recipe data) are read only through their public RSS feed: one request per run, never the post pages, never an archive or private API, never anything behind a paywall. A post is kept only when it holds a recipe (`crawler/lib/post.mjs` decides), and what's kept is the same short list as for a site. Kyle's decision (2026-11-11): Substack's terms bar crawling and scraping, and reading only the feed it publishes for feed readers while keeping this little is the line we hold; writers aren't messaged first for now. The About page promises removal within a week to anyone who asks, so honor it: set the source to `link-only` or take it out. The full note is in KitchenCatalog's `recipe-sources/schema.md` under `feed`. Each newsletter still has to be one Kyle picked.
- YouTube only through the official YouTube Data API. Refresh stored video data at least every 30 days (the weekly run does), drop removed or private videos, and label video results clearly as YouTube.
- The YouTube key lives in the GitHub Actions secret `YOUTUBE_API_KEY`. Never in code, the site, or a chat.
- Adding a source means checking robots.txt, terms and whether it publishes recipe data first, and recording the result in KitchenCatalog's `recipe-sources/sources.json` and Confluence. To add or change a source, edit that file in kyle-pace/kitchen-catalog (`node js/test.mjs` checks it), push it, then run `npm run sync-catalog` here and commit the copy. Only `vetted: true` sources are used.
- **A site that says no to AI training** (Ozlem's Turkish Table's robots.txt: `Content-Signal: search=yes, ai-train=no`; added 2026-11-18, Kyle's call) is fine to index for search. Never use the index to train or tune a model, and check a site's signal before any new use of its recipes beyond finding and linking to them.
- A test crawl comes before a new site's first full one: `node crawler/crawl.mjs --sources <id> --limit 6 --dry-run --no-videos --sample 2`. Look for a sitemap that lists pages that aren't recipes (give the source an `include` pattern in KitchenCatalog; Pati Jinich's lists dish and series pages, Ozlem's its home page) and for one that comes back empty (Swasthi's Recipes, paused 2026-11-18).
- A site that writes each recipe's name as several search phrases in a row (Hebbar's Kitchen: "methi paratha recipe | methi ka paratha | …") gets `crawl.name_split` in KitchenCatalog; `firstName()` in `crawler/lib/extract.mjs` keeps the first phrase and gives it capitals. Only for sources that ask, since other sites use " | " in real names. Sites with copies in other languages get an `include` that leaves them out (Hebbar's `/hi/`, My Colombian Recipes' `/es/`).
- Microdata is read for the recipe's own properties only: an item nested inside it (ahnest kitchen's author, a `Person` whose name comes first) is skipped by `nestedScopes()` in `crawler/lib/extract.mjs` (2026-11-18), or its name would become the recipe's.
- Serious Eats is not crawled (its owner requires written permission). It's a link-out only, unless permission is given.

### Shared App Projects rules

- Free to run, private by default, no accounts.
- Type is Atkinson Hyperlegible Next (and Mono for code). The display settings panel (theme, text size, font) is on every page.
- Text meets WCAG 2.2 AA contrast. Interface motion under 300 ms, custom easing, only under `prefers-reduced-motion: no-preference`.
- Ingredient names come from KitchenCatalog (kyle-pace/kitchen-catalog, which has a JS matcher), so ids match Grocery Deals and Henwood.
- Pantry data never comes to this site. "Use what I have" in the app belongs in Henwood, reading this site's static index; on the web it's typed in. The one exception is Grocery Deals' list lookup (next section), which Kyle approved on 2026-11-14: a few catalog ids, never typed text, answered and forgotten.

### The app (findish-app) stays in step

Findish also has an iPhone and iPad app, `kyle-pace/findish-app` (private), checked out next to this repo. It reads `https://findish.now/index.json` and runs this repo's `src/lib/search-core.mjs` on the device, bundled by its `App/update-search.sh`. [docs/web-and-app.md](docs/web-and-app.md) is the agreement between the two: what they share, the rules, and a table of which features each side has. In short:

- Search and ranking change here only. After a merge that changes `search-core.mjs`, rebundle the app (`App/update-search.sh` there) and commit it.
- `index.json` only grows: add fields, never remove, rename, reorder or retype one until an app version that copes is out.
- A pull request that adds or changes a feature people see updates the feature table in `docs/web-and-app.md`.
- Same event names and the same on-screen words on both sides.

### Layout

- Sources: every source, how it's collected, the result of its last check and ways to support its creator live in KitchenCatalog (`recipe-sources/sources.json`, field reference in `recipe-sources/schema.md`), vendored to `vendor/kitchen-catalog/sources.json`. `crawler/lib/sources.mjs` turns it into the crawl jobs, YouTube channels, link-outs and support links the crawler and `scripts/build-index.mjs` use.
- `crawler/`: the weekly crawl (`node crawler/crawl.mjs`, options at the top of the file). `npm test` runs its tests. GitHub Actions runs it every Monday (`.github/workflows/crawl.yml`) and commits the results; run it by hand from the Actions tab with a small `limit` to test.
- **Crawls of different sites can run side by side** (since 2026-11-18, Kyle's call, after a night of adding sites one batch behind another). A hand-started crawl of named sources is its own concurrency group; the weekly run, a push's smoke test and a hand-started crawl of everything share one. A run's title says what it reads ("Crawl: woks,sk" or "Crawl: all sites"), and its first step (`crawler/check-turn.mjs`, rules in `crawler/lib/turns.mjs`) stands it down when a run that started earlier is reading one of the same sites, so a site still only ever gets one request at a time: a push's smoke test skips, a weekly or hand-started run fails with a message and is started again later. A smoke test never stands a real crawl down (Kyle's call, 2026-11-19): with only smoke tests ahead of it, a crawl waits for them, a minute at a time for up to 25 (`turn()` in `turns.mjs`). It stands down instead of waiting so it doesn't use build minutes doing nothing. Saving is `crawler/save-crawl.sh`: it takes main as it is now, lays this run's files over it and joins the two runs' counts in `data/status.json` (`mergeStatus()`: this run's word for the sources it read, the saved word for the rest), then tries again if main moved. A run fails on its own alerts only, not ones another run saved.
- Feed sources: a source with a `feed` section (instead of `crawl`) is read by `crawlFeed` in `crawler/crawl.mjs`. `crawler/lib/feed.mjs` reads the RSS; `crawler/lib/post.mjs` keeps a post only if it has a run of ingredient lines with amounts plus a sign it's a recipe (an Ingredients or Method label, a "Serves 4" line, or steps starting with cooking verbs). The dish's own heading becomes the name and the post's title a keyword. A feed lists only the newest posts (about 20), so recipes stay after their post leaves the feed, and there is no back catalogue. To switch a newsletter on: in KitchenCatalog set it `vetted: true` with its home as `url`, `collect.status: crawl` and `"feed": { "url": "/feed", "default_cuisine": "…" }`, sync, and add its photo host (`substackcdn.com` for Substack) to `.agents/allowed-hosts.txt`.
- `data/<id>.json`: what we keep per recipe (n name, u link, t minutes, c cuisine, k course, y yield, i ingredient names, img photo link, kw keywords) or per video. `data/status.json`: the last run's counts and alerts; each source's `count` is what it kept, and `previous` what it had kept the run before (the index build compares against both, see "The build has a floor").
- `state/<id>.json`: every page seen, its sitemap lastmod, whether it had a recipe and when it was fetched, so only new or changed pages are fetched.
- `prototype/`: the November 1, 2026 prototype. `python3 prototype/build.py` writes `prototype/index.html` from `template.html` and the sample data in `prototype/data/`. Published as a private Claude artifact; see Confluence for the link.

### The search page

- Live at [findish.now](https://findish.now/) since 2026-11-16 (before that kylepace.dev/recipe-search/). It's its own Cloudflare Worker (`recipe-search`) with findish.now as its Custom Domain (`wrangler.jsonc`); the zone is in Kyle's Cloudflare account, registered at Porkbun. The kylepace.dev hub (`public/_redirects` there) forwards every old /recipe-search/ address here with a 308, which keeps POSTs to /mcp and /api/with working for older Grocery Deals and Henwood builds. Still listed on kylepace.dev's Labs. Cloudflare Workers Builds deploys `main` (build `npm run build`, deploy `npx wrangler deploy`), so every weekly crawl that lands on `main` ships a fresh index.
- Old addresses: `src/pages/recipe-search/[...path].ts` answers the two kylepace.dev Worker routes Cloudflare still sends here and 308s each one to the same path on findish.now, query included. Delete it only after those routes are removed in Cloudflare (the hub's `public/_redirects` takes over then).
- The site serves everything at the root: pages in `src/pages/`, its script `src/scripts/search.ts`, public files (favicon, robots.txt, sitemap.xml, share cards) in `public/`, built assets in `/_astro/`, and its own 404 page. Add new pages to `src/pages/sitemap.xml.ts`. The `google-site-verification` meta tag in `src/pages/index.astro` verifies findish.now in Google Search Console (added 2026-11-16); keep it, or the site loses verification. The home page also carries `WebSite` structured data (with a SearchAction for `?q=`) and Kyle's `Person` as publisher. A link with only `?q=` is read as a typed sentence (see "The features round").
- `scripts/build-index.mjs` turns `data/` into `public/index.json` (generated, not committed) before every build. It matches ingredient lines with the vendored KitchenCatalog in `vendor/kitchen-catalog/`; refresh that copy with `npm run sync-catalog` (expects a clone at `../kitchen-catalog`). **The sync refuses to take things away** (`scripts/sync-guard.mjs`, since 2026-11-17): it stops, copying nothing, when a source or an ingredient id in the copy here is missing from the clone, which means the clone is behind (`git pull` there) or something was added to the copy by hand; `--allow-drop` goes ahead for a source removed on purpose. `scripts/sync-guard.test.mjs` also checks the copy holds together (valid sources, every parent real). When KitchenCatalog splits an item into kinds (fresh herbs into basil, cilantro and the rest on 2026-11-17), the home page's ideas and the `/with/` pages leave out the kinds of anything they already left out (`NOT_POPULAR` in `build-index.mjs`, `SKIP_INGREDIENTS` in `src/lib/browse.ts`), and the search tests that need "a word that is only another item's other name" find one in the index (`otherNameOnly()` in `search-core.test.mjs`) instead of naming it. `node scripts/build-index.mjs --report` lists the most common lines the catalog doesn't know yet, which belong in KitchenCatalog, not here. Pages a site marks up as a recipe that aren't one (a shopping list, a roundup) are left out by hand in `scripts/not-recipes.mjs` (added 2026-11-16), by source id and link; their data stays in `data/` so they aren't refetched.
- **How the page gets the index** (since 2026-11-17; before that it downloaded `index.json` itself, 2.3 MB, about 590 KB compressed, again after every deploy). The build writes the index twice:
  - `public/index.json`, in full, at the same address and in the same shape as always. The MCP server, Ask and `/api/with` (`src/mcp/load-index.ts`), the build-time pages (`src/lib/creators.ts`, `src/lib/browse.ts`, About, How it's built), `scripts/ask-eval.mjs` and Grocery Deals' site build read it. **Don't change its shape or path** without changing them.
  - The page's copy, packed by `src/lib/index-format.mjs`: `public/i/recipes.<hash>.json` (everything but the video rows; about 1.2 MB, 290 KB compressed) and `public/i/videos.<hash>.json` (the video rows; about 510 KB, 170 KB compressed). The hash is of the file's contents, and `public/_headers` serves `/i/*` with `Cache-Control: public, max-age=31536000, immutable`, so a browser downloads each once and again only after a crawl changes it. The build empties `public/i/` first, so only the current pair is deployed. All of it is generated and not committed.
  - `public/index-files.json` (generated) holds the two names plus the only things that change daily, the build date and each recipe's opens (`[row, opens]` pairs, from `data/popularity.json`). `src/pages/index.astro` writes it into the home page as `<script type="application/json" id="index-files">` and preloads the recipes file. Keeping the daily numbers out of the hashed files is what lets them stay cached for a week; don't add anything that changes daily to them.
  - **What the packing does:** columns instead of rows; each recipe's ingredients as only the ones it names (a pantry basic is written as `~position`, a negative number), with the parents (`pos`) and the non-basics (`own`) worked out again in the browser from each ingredient's parents; a link that ends in the recipe's own name as `/*/`; the start every photo from one site shares written once (`photoStarts`); a video's ingredient as one position. `unpack()` gives back exactly `index.json` (`pack()` checks every row and throws, failing the build, if one wouldn't survive), so the search never sees the difference. `src/lib/index-format.test.mjs` holds it to that: the unpacked files deep-equal `index.json`, and the ranking fixture's dish searches plus ingredient, diet, creator and sentence searches return identical results from both. If you add a field to the index in `scripts/build-index.mjs`, a top-level one rides along by itself; a new row position needs a column in `pack()` and `unpack()` (the test fails until it has one). `FORMAT` is the format's version; a page that meets a newer one falls back to `index.json`.
  - **Loading** is `src/scripts/index-load.ts`: fetch the recipes file, unpack it, get it ready with search-core's `prepareSteps()` a thousand recipes at a time with a pause between (so a slow phone still answers taps: the longest stretch the page is busy went from about 300 ms to under 100 ms at 4x CPU slowdown), hand it to `search.ts`, which draws the page; then fetch the videos file and `addVideos()`, after which `videosLanded()` in `search.ts` draws a search again with them. Until the videos land, a search shows recipes only, typo fixing goes by the recipes' words alone (so a fix can change when they land, rarely), and a search only videos could answer (`show=videos`, a YouTube-only creator, no recipe matches) says "Loading videos…" instead of "nothing matches". If the recipes file can't be had (a page left open across a deploy), the loader falls back to `/index.json` for everything. If only the videos file can't be had, `/index.json`'s video rows are used only when it is the same index (`sameLists()`: same crawl, channels and ingredients in the same order); a newer one's rows would point at the wrong channels and ingredients, so the visit goes without videos (`videoRowsFor()` in `index-format.mjs`, tested; it never throws) and a search for videos says "The videos didn't load this time. Refresh the page to try again."
  - **Measured** on Slow 4G (1.6 Mbps, 150 ms) with 4x CPU slowdown, local build, 2026-11-17: search ready in 2.5 s (was 4.1 s), `/?q=tofu` results at 2.5 s (was 4.2 s) with videos at about 3.6 s, a repeat visit 0.5 s (was 3.6 s when the index had changed).
- **The build has a floor** (`scripts/index-floor.mjs`, since 2026-11-17): `build-index.mjs` exits 1, before writing anything, when a crawled site or channel has under 80% of what the last crawl counted for it in `data/status.json` (the larger of `count` and `previous`, the count from the run before, which the crawler now records), when a site or channel the last crawl kept more than 20 from isn't in today's list of sources at all (named in the message; a source that's `paused` in the list is fine), when all the recipes together or all the videos together are under 80%, or when there are no recipes at all. Recipes and videos are added up apart since 2026-11-17: on one grand total (about 13,400) the 20% allowance was 2,700, more than the biggest site (1,541), so a whole site could vanish unnoticed. Sources with 20 or fewer aren't checked on their own. It catches a data file that's missing, empty or cut short, and a crawl that came back thin; a failed build leaves the live site on the index it has. A real drop, or a source taken off the list on purpose, passes after the next weekly crawl (when `previous` catches up and the crawl stops counting it) or at once with `node scripts/build-index.mjs --allow-drop` (`ALLOW_INDEX_DROP=1 npm run build`). Tests: `scripts/index-floor.test.mjs`, including a run of the real script on a small copy of the data.
- **The search itself is one file**, `src/lib/search-core.mjs` (since 2026-11-17), run by the page, the MCP server and Ask, so all three find and rank the same way. `src/scripts/search.ts` is only the page (box, tags, suggestions, filters, address) and hands the core its state; `src/mcp/search.mjs` turns an assistant's arguments into the same kind of state. Change a search rule in the core and nowhere else. It ships to the browser, so keep it small (it added about 4.5 KB compressed to the page's script). Its types for the page are in `src/lib/search-core.d.mts`. Tests: `src/lib/search-core.test.mjs` (against the real index, which `src/lib/test-index.mjs` builds if it's missing) and `src/lib/ranking.test.mjs`, a fixture of 26 everyday dish searches whose checks describe the top of each list (the top three are that dish, no sauce, drink or how-to, the exact name first) rather than naming recipes, so a weekly crawl doesn't break it. `npm test` runs in every crawl after its data is saved (before it, until 2026-11-19, when a failing check threw away a five-hour crawl), so new data that breaks the fixture turns the run red without losing the crawl: look at the list before changing a check. The rules:
  - **Words** (`words`, `stem`): lowercase, accents off, split on anything that isn't a letter, number or mark, in any script. Latin words are made singular (cookie = cookies, pie = pies, leaves = leaf; `IRREGULAR` holds the exceptions, and "fries" is kept apart from "fry"). Spellings that mean the same thing are folded to one by the `EQUAL` table (chili/chilli/chile, yogurt/yoghurt, donut/doughnut, bbq/barbecue, jjigae/jigae/chigae, tteokbokki/ddukbokki/topokki, lasagna/lasagne), for index words and typed words alike: add a group there when a spelling splits results. Words in Chinese, Japanese, Korean or Thai match as a piece of a name. A query with no words in it ("???") finds nothing, not everything.
  - **Filler** (`STOP`: "easy", "recipe", "everything", "has", "that", "you"…) is ignored when other words remain; a search made only of filler keeps its words ("easy dinner").
  - **Whole words after Enter, unfinished words while typing**: only the suggestions (`typing: true`) let the last word be the start of one; after Enter "gin" is gin, not ginger, unless a word is nothing but the start of others ("dumpl"). Ingredients' other names only ever match as whole words. A word finds a recipe through an ingredient only when the search has that ingredient's whole name (`ingWord` in `prepareSteps`, `term`): "green onion" and "scallions" find what uses green onions, but "salad" doesn't (it was matching the other name "salad onions": 1,726 results, now 371), and "chicken" doesn't find chicken broth concentrate. Words for the state it's in (fresh, dried, ground, whole, leaves, seeds) aren't needed, and an other name with a filler word in it ("chicken for stir fry") is a note, not a name.
  - **Typos** (`queryWords`): a word the index doesn't know is swapped for the closest one (fewest edits, then the longest shared start, so "kimchee" isn't "kitchen"), choosing the candidate that finds the most with the other words; words are joined or split when the index writes them that way ("pot sticker", "stirfry", "bi bim bap"); and when a search of several words finds fewer than 3, a real word one letter off is tried ("pad tai"), counted on names only. A fix is kept only if it finds something, and never when nothing typed was right ("xyzzy plugh" finds nothing). A word nothing has is dropped and reported (`ignored`) when another word or a tag carries the search. `exact` turns all of it off, and adding a tag resets it.
  - **Understanding a sentence** (`understand`, on Enter and for the MCP `query`): time ("under 30 minutes", "quick"; a small number with no "under" or "in" is a dish, "7 minute eggs"; when nothing is called that, `queryWords` sets the number and its unit aside and says so, so it finds eggs), diet, creators, leaving out ("no pork", "dairy free", "without cilantro"; the list after "no" is read word by word in `cutLeaveOuts`, never with one pattern, see "No pattern that can stall" below; at most 8 things; a comma before "with" ends it; "not" only before an ingredient, so "not your average chili" is a dish), cuisines said as one ("thai food", "mexican dinner", "thai desserts"; a bare "thai" stays a word unless other tags were understood), ingredients ("with tofu and eggs", "i have chicken, kale", comma lists; after a dish only an ingredient's own name is tagged, so "pasta with tomato sauce" stays words; "have a cold" is left alone), courses ("desserts", "side dishes", "starters" always; "breakfast", "snacks", "drinks" only on their own; "soup", "salad" and "bread" stay words because they name dishes), and "videos". Typed, pasted and "i have…" lists give the same tags: the page's comma handler tags each finished piece and sets `state.list`, so Enter carries on the list.
  - **Creators**: a creator's name words and their other names (`CREATOR_ALIASES`: Pailin, Nagi, Deb Perelman, Kenji…) are kept apart. Recognised by full name, the name without "the", then other names, longest first, before cuisines ("chinese cooking demystified" is a channel). Names that are common words (`WEAK_ALIASES`: "lau") need "from" or "by". Add other names there, not in the page.
  - **Ranking** (`textScore`, `search`): per word, in the name 8, in a bracketed part of it or as the start of a word 6, keywords or cuisine 3, an ingredient's name 2, the site's name 1. Then the words in order in the name +10 (+5 inside brackets), how much of the name they cover up to +6, and the name being exactly the words +6. Popularity adds up to 4 (log scale), but at most 1 for a recipe that only matched by keyword or ingredient. Sauce and drink courses −4 unless the words ask for one (`SAUCY`) or a course is picked; "How to…" pages −3 unless "how to" was typed. Order: with words, score first (then more of your ingredients, then fewer others); with two or more ingredient tags and no words, most of them used, then fewest others; with one ingredient or filters only, score (a name that says the ingredient +3, a main +1, a recipe of one or two ingredients −3, so "rice" brings fried rice, not how to steam it). Ties: photo, opens, name. There is no shortest-time tie-break any more. Creators take turns among close calls (`mix`).
  - **Videos** (`searchVideos`): words must all be in the title, never the channel's name; best title match first (the phrase in order, then how much of the title it is), newest among equals, channels taking turns. A video is left out when its title names something being left out, or meat or fish on a vegetarian search; a cuisine keeps channels whose creator cooks it (`cuisine` on each channel in the index, from KitchenCatalog's first cuisine) and titles that name it; a time limit or "new this week" shows none.
  - **No pattern that can stall** (2026-11-17): the search rules run on text from anyone (`/mcp` takes 200 characters, a `?q=` link any length), so no regular expression there may nest one repeat inside another or put a lazy group inside a repeat. The old "no …" pattern did, and `no a or a or a…` took 42 seconds at 96 characters; a run of punctuation in a long link froze `cleanQ` for 28 seconds. Now the list after "no" is read a word at a time, `cleanQ` trims with a loop and stops at 400 characters (`MAX_Q`, as long as a question to Ask), and `understand` reads at most 400. `src/lib/slow-sentences.mjs` holds sentences built to be slow; the tests run them through `understand` and the MCP's `searchRecipes` and fail over 50 ms. Run them after touching any pattern in `src/lib`, `src/mcp` or `src/chat`.
  - **"Veggie"** means vegetarian ("veggie pasta") unless a meat or fish ingredient is in the sentence ("chicken veggie stir fry" is chicken with vegetables); "veggie burger" is vegetarian and keeps its words.
  - **A question's own words** are filler (`STOP`): step, instructions, goes, tell, help, kids, mom and the like, so "how do I make mapo tofu step by step instructions", "what goes with bulgogi" and "my mom's chicken soup" find the dish.
  - **Suggestions rank only what they show**: the search box asks `search(…, { first: 4 })`, which puts in order just the recipes that could be in the first four (the same four as the full search; `.total` is how many matched). About 1.25 ms to 0.8 ms a keystroke on a laptop, the worst from 4.1 to 1.8.
- **Diet and leaving things out** (`scripts/diet.mjs`, since 2026-11-17): the index build gives each recipe a set of flags (row position 12, left off when zero; videos carry theirs at position 6) for meat, fish, dairy, egg, other animal products (honey), nuts, shellfish and pork, read from three places: the catalog items its lines matched, each line's own words, and its name. Vegetarian and vegan go by those flags, so "Korean Fried Chicken" is out whatever its ingredient list matched. Since 2026-11-17 a line the catalog matched is read by its words too (`lineFlags`), for meat and fish only: "tuna in olive oil" matches olive oil, and "hot dogs", schmaltz, snails, gelatin, hen, whiting and shumai are in the word lists. The words win the other way as well: "vegan chicken", "mushroom stock" and "hot dog buns" matched to chicken, stock and hot dogs aren't flagged. A line that leaves the choice to the cook isn't flagged (Kyle's review, 2026-11-17): "chicken or vegetable stock", "beef broth or water", and for a matched line with no meat in its item, any "lard or butter". A bare "stock" still counts as meat. Names are also read for dishes that are meat unless they say otherwise (`MEAT_DISH`, `PORK_DISH`: burger, katsu, karaage, katsudon, gyudon, oyakodon, carbonara, bolognese, schnitzel, chashu, yakiniku, sukiyaki, shabu, bossam, laab, satay, pho, pot roast and more), which is all a video has; a plant word before or after ("black bean burgers", "tofu katsu", "karaage okra"), "vegan" or "vegetarian" in the name, or a shelf word after ("burger buns", "satay sauce") clears it, and they aren't read in ingredient lines. White chocolate counts as dairy; plain and dark don't. That round took 87 videos and 14 recipes off vegetarian searches and put 34 recipes back (2,443 to 2,463 recipes, 3,685 to 3,603 videos). A recipe with no ingredient list gets every flag and is never offered as vegetarian or free of anything. Plant versions are known by the word next to them ("coconut milk", "vegetarian oyster sauce", "tofu steak"). `index.groups` lists what can be left out as a whole (dairy, eggs, nuts, shellfish, pork, meat, seafood; ids `any-dairy`…); the core appends them after the real ingredients, so a "no dairy" tag, `without=any-dairy` in an address and the MCP `without` all hold one like any ingredient. "No pork" means the group (bacon, ham and lard too). Gluten is left out on purpose: soy sauce, noodles and stock hide it, and a half-right answer is worse than none. All of it is a best guess, and the About page and the MCP notes say so. `index.diet` (ingredient positions) is still written for Grocery Deals' site build.

### The MCP endpoint

- `findish.now/mcp` lets AI assistants search the index over MCP (Streamable HTTP), added 2026-11-11. Two read-only tools, `search_recipes` and `list_sources`, and three ready-made prompts (`cook_with`, `find_dish`, `whats_new`). No sign-in, no analytics, and it never logs what was asked.
- It's an Astro endpoint (`src/pages/mcp.ts`, `prerender = false`), the only part of the site that runs on the server; the pages stay static files. It reads `index.json` (the full index; the page loads a packed copy of the same thing, see "How the page gets the index"), through the Worker's `ASSETS` binding, once per isolate: `src/mcp/load-index.ts` is the one loader, shared with Ask and the list endpoint, so a running Worker holds one parsed copy (since 2026-11-17; before that each endpoint kept its own). Built on `createMcpHandler` from Cloudflare's Agents SDK (`agents`) with MCP SDK v2 (`@modelcontextprotocol/server`) and `zod`; stateless, no Durable Object. `nodejs_compat` in `wrangler.jsonc` is for it.
- The search is the page's own: `src/mcp/search.mjs` turns the arguments into a search for `src/lib/search-core.mjs` (see "The search itself is one file" above), typo fixing included. If the index's shape changes in `scripts/build-index.mjs`, update `prepare()` in the core.
- `searchRecipes` arguments (all optional): `query`, `ingredients`, `without`, `diet`, `cuisine`, `course`, `max_minutes`, `creator`, `limit` (1 to 30), and since 2026-11-17 `new_only` (bool), `show` (`both` | `recipes` | `videos`; the older `videos: false` still means recipes), `sort` (`best` | `quickest` | `newest` | `random`) and `offset`. List arguments may arrive as one comma-separated item. The tool's schema in `src/pages/mcp.ts` has to list an argument for it to reach the search (zod drops what it doesn't know), and Ask's tool in `src/chat/chat.mjs` uses the same names.
- What the answer adds, only when there is something to say: `understood` (what was taken out of `query` and searched as a filter: "quick vegetarian pad thai" becomes max_minutes 30, diet vegetarian, query "pad thai"; an argument given outright wins), `corrected` (`[{ from, to }]`), `leaving_out` (names of what was left out; a word in quotes means it could only go by recipe names), `relaxed` (when nothing matched everything: `counts` for each single change that would find something, and `dropped`, `total_recipes` and `recipes` for the gentlest one, in the order time, new-only, an ingredient, cuisine, creator, course, the words; `total_recipes` and `recipes` at the top stay 0 and empty, and what's being left out is never dropped), plus `new: true` on a recipe found this week and `total_videos` when only videos are asked for.
- `without` leaves out an ingredient only by its own name, or a group (dairy, eggs, nuts, shellfish, pork, meat, seafood). A word that is only another item's other name ("shiitake", filed under Mushrooms) can only be left out by recipe name, and the notes say that instead of quietly dropping every mushroom. (Until 2026-11-17 cilantro was the example: KitchenCatalog now has basil, cilantro, parsley, mint, dill and chives as their own items under Fresh Herbs, and lemons and limes apart, so each can be searched for and left out by name.) Groups and diets are called a best guess in the notes and in the server's instructions in `mcp.ts`.
- A creator is found by id, name, the name without "the", another name ("Pailin"), whole words of the name ("woks") or their site's address, with three letters at least. One with only a channel gets a note that there are no recipes to list.
- Protocol details (2026-11-17, server version 0.2.0; bump `VERSION` in `mcp.ts` whenever tools, arguments or answers change):
  - Both tools have an `outputSchema` and answer with `structuredContent` as well as the same JSON as text. The schemas are loose on purpose (only names and links are required, extra fields allowed), so the search can add fields without the SDK rejecting its own answer. If you rename or retype a field the schema names, change the schema in the same commit.
  - Any website's page may call it (`allowedOriginHostnames: '*'`). The SDK's default 403s every `Origin` but localhost, which locked out assistants that run in a browser. The check exists to protect sign-ins and servers on a visitor's own machine; this server has no sign-in or cookies, only reads, and serves the same public index to everyone. The `Host` check (`allowedHostnames`) stays. If the server ever gets sign-in or anything per-person, this has to go back to a list.
  - It says `listChanged: false` for tools and prompts: it's stateless, so it can never send that notice.
  - The server's instructions and tool descriptions say what the index lacks (method, amounts, servings, nutrition, spice, equipment), that cuisine, course and time labels are sparse and filtering on one hides unlabeled recipes, that some creators are videos only, and that vegetarian, vegan and `without` are best guesses. The fractions in the instructions (about a quarter with no cuisine, an eighth with no course, a twelfth with no time) were measured on 2026-11-17; re-measure if the index changes a lot.
- The collecting rules apply here as well: results are names, links, ingredient names, time and cuisine, never the method, and the server's instructions tell assistants to send people to the original. Pantry data still never comes to this site: ingredients arrive as typed words, like on the page.
- `npm test` covers the rules; `npm run try-mcp` calls every tool with the official client (against `npm run preview`, or pass the live address); it also checks the argument list, the output schemas, the prompts and that a request carrying another site's `Origin` is answered.
- `/assistants/` (`src/pages/assistants.astro`, added 2026-11-15) is the page for people connecting an assistant, modeled on Grocery Deals' `/mcp/`: an Add to Claude button (a prefilled claude.ai link that Claude doesn't document, tested 2026-11-11), the address with a copy button and the written steps, things to ask, what it can look up, and what it keeps (nothing). A browser that opens the MCP address is sent there. The About page's `#assistants` section is a short version with the same button and a link to it. The address, the Claude link and both page paths live in `src/lib/assistants.ts`: if the server moves, change it there (plus the routes in `wrangler.jsonc` and `allowedHostnames` in `mcp.ts`). `src/scripts/assistants.ts` wires the buttons and sends "Opened Add to Claude" and "Copied MCP Address" (`added_from`: the page).
- `/privacy/` (`src/pages/privacy.astro`, added 2026-11-15) is the search's own privacy page and the privacy policy URL for a Connectors Directory listing: the page, anonymous usage (with an opt-out switch), the MCP server, the Grocery Deals list lookup, who else is involved, retention and contact. Change it, and its date, whenever what's collected changes. The About page's Privacy section links to it.
- The reading pages (About, assistants, privacy) share `src/styles/prose.css` (`<article class="prose">`).
- Both tools carry a `title` and `readOnlyHint`, which the Connectors Directory requires.
- Seattle Grocery Deals has a sister server (`mcp/` in its repo, at mcp.seattlegrocery.deals) and stays separate on purpose (Kyle, 2026-11-11): recipes are for anyone, deals are only for Seattle. Henwood's is local, in the Mac app.

### Ask (the chat experiment)

- Started 2026-11-16 (Kyle's call): describe what you want in your own words ("what can I make with fish, kimchi and onions?") and the page shows the search for it. Only offered at `findish.now/?chat=1` (remembered for the visit in that tab, in `sessionStorage`); not linked anywhere yet.
- `src/chat/chat.mjs` is the logic, with no network code. Claude (Haiku 5.5) gets two tools: `search_recipes`, to check a search and loosen one that finds fewer than 3, and `show_results`, the search to show plus a sentence or two (and `sides_for`, the dish that "what goes with bulgogi" named). At most 3 searches per message, 400 characters per message, 4 messages per chat. Tests with a pretend Claude in `src/chat/chat.test.mjs`. What changed on 2026-11-17, and why:
  - **The check is the page's search.** Each `search_recipes` call is first turned into the page's address parameters (`pageQuery`), then read back the way the page's `readUrl` reads them (`stateFor`) (a `q` in an address Ask hands over stays plain words: only a fresh link that is nothing but `?q=` is read as a sentence) and run through `src/lib/search-core.mjs` with the same steps as the page's `render()` (`searchShown`: every word, then most of the words, videos alongside), so the count Claude sees is for the search the page will show. Ask does not go through `searchRecipes` in `src/mcp/search.mjs`: that one lifts phrases out of `query` into filters, which the page never does to a `q=` in an address, so the counts would drift. If `readUrl` or `render()` change how a search is read or run, change `stateFor` and `searchShown` to match; a test compares them with the core, and another checks that Ask and the MCP search agree on plain searches. When a check finds nothing, `relaxed.counts` says how many each single loosening would find (the time limit, each ingredient, the cuisine; never the course or what's left out). What couldn't be kept (an unknown creator or cuisine) comes back as a note with the list of real ones. Words go to the page as typed, so the page's own typo fixing applies, and `corrected` tells Claude what it fixed.
  - **Claude sees videos** (counts and a few titles), creators who are videos only (marked in the `creator` description, built from the index), `new_only` ("what's new", `new=1`) and `show` (`show=recipes|videos`). `cuisine` and `course` are enums built from the index. `toolsFor(ready)` builds the tools once per loaded index.
  - **Leaving out is by an ingredient's own name, or a whole group.** Leaving out a word that is only another item's other name ("shiitake" under Mushrooms; cilantro under Fresh herbs until it got its own item on 2026-11-17) used to leave out the whole item; now only a main-name match becomes `without=`, and anything else is kept out of names with `not=`, as on the page. "No dairy" is the group (`without=any-dairy`; also eggs, nuts, shellfish, pork, meat, seafood), which the instructions tell Claude to use instead of listing milk, cheese and butter. An ingredient said the long way ("boneless skinless chicken thighs") is found by the longest ingredient name inside it.
  - **`guardReply()` enforces the reply rules in code:** a sentence that contains the name (two words or more) of a recipe or video Claude was shown is dropped, unless the person or the search's own words said it ("mapo tofu"); a sentence with a count ("12 recipes") is dropped unless the number is the real count for the shown search. If nothing is left, the reply is "Here’s a search for that."
  - **Instructions** (`SYSTEM`): dish words only when a dish was named, course words go in `course`, fix spelling and write dishes in Latin letters whatever script was typed, loosen in the order time, least important ingredient, cuisine (never the course, `without` or `diet`), say plainly what can't be filtered (servings, nutrition, spice, equipment), and resend the whole search on a follow-up. `SYSTEM` and the tools must stay the same from request to request (no dates, nothing per-person), or the prompt cache below stops working.
- `src/chat/anthropic.mjs` is the one file that talks to Anthropic (plain `fetch`, no SDK). Each request gives up after 8 seconds and a whole message after 15 (`LIMITS.callMs`, `LIMITS.turnMs`); a 429 or 529 is tried once more. The instructions and tools are marked for prompt caching, so the second and third request of a message, and anyone asking within five minutes, read them at a tenth of the price. **Before switching models, read the comment at the top of that file:** Ask forces a tool on every call, which Haiku 5.5 allows and Sonnet 5.5 and Opus 5.5 reject with a 400. The key is the Worker secret `ANTHROPIC_API_KEY` (set in the Cloudflare dashboard, never in code), in an Anthropic workspace with its own monthly spend limit. Kyle's Max plan API credits cover it.
- Failures have short names, never text: `timeout`, `refusal` (Claude declined), `max_tokens` (cut off), `no_tool`, `no_show`, `http_<status>`, `network`, `bad_answer`.
- `POST /api/chat` (`src/pages/api/chat.ts`) takes `{"messages": [{"role": "user", "content"}, {"role": "assistant", "showed": "<the search the page showed>"}, ...]}` and answers `{"reply", "query", "searches", "found"}` (`searches`: how many checks Claude ran; `found`: recipes plus videos the server's copy of the search found).
  - **Only the person's turns are read as text.** From an earlier answer only the search is kept (`showed`, or the `[showed: …]` the current page appends to `content`), checked against the index and rebuilt on the server, so a request can't put words in Claude's mouth.
  - The body must be `application/json` (which also stops another site's page from posting to it) and is read as a stream that stops at 8 KB (`src/chat/request.mjs`).
  - Two Workers rate limits in `wrangler.jsonc`: 6 a minute per visitor (keyed by IP in memory only; an IPv6 visitor by their /64 block, since one person can hold billions of addresses) and 20 a minute for everyone (60 until 2026-11-17). **If either limiter binding or the key is missing, Ask answers `"fallback": "off"`**; it never runs unguarded.
  - Over a limit, off, or if Claude fails, it answers `{"fallback": "busy"|"off"|"error", "reason": "<short name>"}` with a plain search of the person's words, so the page never breaks. The one log line is `ask <status> <fallback>:<reason>`; what was typed is never logged or kept.
  - The rate limits bound requests per minute, not a day's bill: the workspace spend limit is the real cap. A daily counter would need KV or a Durable Object (Kyle's call; not built).
- It lives in the search box itself (Kyle's call, 2026-11-16: not a separate chat panel), and **nothing is sent without the person choosing it** (since 2026-11-17). While what's typed `looksLikeAsk()` (in `src/lib/search-core.mjs`: a question mark, a question or request word first such as what, how, can, show or make, or a sentence of five or more words that starts with or holds words like "I have", "my", "leftover", "go with"), the suggestions show only two options: "Ask: …" with the line "Sent to Claude to turn into a search. Not kept.", and "Search for these words" ("Searched here, on your device."). No other suggestions show under a question, and its commas stay (it isn't a list of tags). `goesToAsk()` in `src/lib/page-state.mjs` (tested) is the whole rule for Enter: Ask gets it only from the "Ask" option, or when it reads like a question and the person has already picked Ask this visit (`findish-ask-chosen` in sessionStorage), or while Ask's results are up (`data-from-ask`), when everything entered carries on that chat and the suggestions lead with "Ask" and "Search for these words". A plain search typed over Ask's results starts clean: it doesn't keep Ask's cuisine, course or tags. `submit()` in `search.ts` sends the question to `src/scripts/chat.ts` as a `findish:ask` event. `chat.ts` (loaded only when Ask is on, with `src/styles/chat.css`) calls `/api/chat` with earlier answers as `{"role": "assistant", "showed": query}` (never reply text), and hands the search back as a `findish:show` event, which `search.ts` shows like any search and reports the result count. The reply is one block above the results: "You asked: …" (a button that puts the question back in the box), the answer, then one small line, "Answered by Claude, Anthropic's AI. What you ask isn't kept. Privacy." with "Search my words instead"; that line only shows once Claude has answered. While waiting, the old results dim, the ideas hide and the button rests (`data-asking`). "Search my words instead", and any fallback or failure, send the words back as a `findish:plain` event, which runs them through `submit()` and `understand()` from a clean search; on a failure the count line starts "Ask isn't available right now, so here's a plain search for your words." After four questions the next one starts a new chat and the block says "Starting over from here." Answers are kept for the visit in sessionStorage (`findish-ask-answers`, the last 8, keyed by the search shown), so a reload or Back shows the answer with its results and the chat carries on. Ask's "what goes with X" puts `sidesFor=<dish>` in the address; `readUrl` reads it (letters only, `dishName()`, and escaped) and the count line says "3 Korean sides to go with bulgogi". Changing the search by hand ends the chat (`writeUrl` drops `data-from-ask`); a random pick doesn't.
- Events: "Chose Ask" and "Chose Plain Search" (`follow_up`: whether Ask's results were up) when one of the two options is picked; "Sent Chat Message" (`turn_number`, `message_length`, `response_ms`, `showed_search`, `result_count`, `searches`: how many searches Claude checked); "Failed Chat Message" (`turn_number`, `message_length`, `response_ms`, `reason`: the server's fallback and reason such as `busy:visitor_limit`, or `http_500`, `network`, `no_reply`); "Tapped Search Instead"; and "Opened Recipe" gets `from_ask: true` while the results are still the ones Ask showed. Never the words typed. (`fell_back` on "Sent Chat Message" is gone: a fallback is a "Failed Chat Message" now.)
- **Test questions:** `scripts/ask-questions.json` holds 42 real questions (two are chats of several turns) with what each search should and shouldn't do; `node scripts/ask-eval.mjs` scores Ask against them on the live site (spaced under the rate limit, about 8 minutes), or `--local` with `ANTHROPIC_API_KEY` set runs it here against `public/index.json` before pushing. `--repeat 3` asks each three times and lists the ones that are only sometimes right. Every answer is also checked two ways against the index: the shown search must find something, and the reply must not name a recipe from its results. `scripts/ask-eval.test.mjs` tests the scorer. **Run it after any change to Ask's instructions or to the search, and after the deploy** (`npm test` only uses a pretend Claude, so it can't tell whether the real one follows the instructions), and add every question it gets wrong.
- Before opening it to everyone: decide whether to keep it, and consider Turnstile (a new host, needs Kyle's OK) if the rate limits aren't enough. The page says what Ask does before anything is sent, and `/privacy/#ask` describes that (2026-11-17).
